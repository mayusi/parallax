Reference

Pipelines

Parallax organises all creative and engineering work into eight pipelines, one per discipline. Every pipeline follows the same shape: start with your request, look up the right case, plan the work, step through numbered stages with approval locks, pass objective gates, track time against a clock, record your verdict, and let the kit learn from it. This page explains that shared shape and links to the detail for each pipeline.

The shape every pipeline shares

Every pipeline follows the same progression. Understanding it once means you can navigate any pipeline.

1. Start with your request

Every pipeline session starts with a single command. You must run it before any build command is accepted; the kit's gate blocks pipeline work without a fresh session token.

lune run parallax start <lane> --prompt "<your request in plain words>"

The --prompt text is compiled by PROMPT-X: it determines the case, the contract floor, the capability menu, and the forbidden routes for this piece. The session token lasts four hours.

The boot sheet follows: the ranked lessons for this lane, the last handoff, any failing gates, and the next suggested action. Read it before doing anything.

2. The case lookup

Your prompt maps to a CASE in the lane: a named scenario with its contract floor (what must be true for a done result), which routes are forbidden, and which capabilities apply. Use kit case <lane> "..." to look up a case directly.

3. The plan

For any heavy build (a hero asset, a hero effect, a hero system), write a plan file at assets/plans/<piece>.plan.json before starting. The kit gate blocks a heavy build without one. The plan records the tools per part and the beat order from the case's capability menu.

4. Stages with approval locks

Every pipeline has numbered stages. Some stages are locked: the next stage cannot start until you approve the current one. Approval always comes from you; no automated score or gate result unlocks an approval stage.

stage N → approval lock (you) → stage N+1

To give approval: kit approve <lane> <name> "<your words>" --by owner --stage <stage>. Some approvals hold only for the exact version you saw (a VFX style sheet, for example): an edited piece needs your approval again.

5. Gates

Between stages, objective gates measure the work. Gates have two effects:

EffectMeaning
blocksThe build cannot proceed. Fix the issue, then run again.
warnsThe build continues, and the warning is shown in the result.

Gates run inside each lane's build commands and inside kit verify. They measure things you should not have to remember to check: topology, remote security, timing, readability, performance thresholds.

6. The clock

In the 3D, VFX, Animation, Worlds, Interfaces and Sound pipelines, every piece runs against a time budget set by its tier. The Gameplay systems and QA pipelines have no clock.

TierBudgetWhen
Simple10 minutesA prop, a single sound, a simple screen.
Complex30 minutesA sound set, a complex screen, an effect.
Hero60 minutesA hero asset, a hero effect, a hero screen. Only with your approval (kit approve).

When the clock runs out, no change to the piece can be built. The piece as it was can still be rebuilt, looked at and played, and shown to you for a verdict. To extend: kit clock <lane> <name> --extend <minutes> "<your words>". To restart from scratch: --restart "<your words>".

Tip

Speed is a quality. A prop in 10 minutes and a hero weapon in 60 minutes that both pass their gates are both good outcomes. The clock is not a soft deadline; it is the production model.

7. Your verdict

When the work is done, you score it from 0 to 10 (or say "keep" or "redo") and say why in a few words:

lune run parallax verdict <kind> <name> <0-10> "one sentence about why"

The score drives two things:

  • Score ≥ 7 (or "keep"): the piece goes into the golden set. Use kit accept <kind> <name> to lock it as a regression floor; no future change may make it worse.
  • Score ≤ 3 (or "redo"): the route that produced this result goes into the graveyard, the record of failed routes that later sessions see when they start. A verdict of 3 or less needs --route "what failed".

8. Lessons

Record what you learned during the session so the next one starts better:

lune run parallax lesson <area> "what I learned" --stage <stage>

Lessons are ranked by relevance to each new piece and shown at the start of its session. A new piece must have its matched lessons answered (applied or explicitly skipped with a reason of at least six words) before its quality locks pass. This prevents the same mistake twice.

How pipelines work together

Most deliverables require more than one pipeline. A combat move needs an animation (from the anim pipeline), hitboxes from the systems pipeline, a sound (from the SFX pipeline), and a visual effect (from the VFX pipeline). These coordinate through the board.

The cross-lane kickoff brief

When a deliverable spans multiple pipelines, start with a kickoff brief. This creates linked tasks on the board for each lane and ensures each lane's session starts with the same context:

lune run parallax kickoff SwordSlash "a sword slash" \
  --anim "a two-hit downward slash, R6, 24 frames at 60 fps" \
  --vfx "a crescent blade trail with impact sparks" \
  --sfx "a metallic cut, heavy thud on hit" \
  --code "applies 20 damage, can parry, 10-frame window"

Each lane then runs its own pipeline independently and links its result back to the kickoff card.

Hand-offs on the board

Every session ends with a handoff, which records what was done, what comes next, and any warnings for the next session. The next session's boot sheet shows the last handoff for the lane.

lune run parallax handoff "built the slash anim, verdict 8" \
  --lane anim \
  --next "VFX lane needs the frame timings from build/animations/Slash.metrics.json" \
  --warn "recovery is 8 frames — shorter than the design page said; VFX hitbox window must match"

Timing data from the animation pipeline flows directly into the systems pipeline's move data via "from_anim" in the move JSON. VFX cue times come from the same frame numbers. This chain means a change in one pipeline's output must trigger a rebuild in the pipelines that depend on it.

The board

All tasks, handoffs, decisions, and verdicts are recorded on the kit's local board. Use kit status to see the whole picture at any time, including which tasks are in progress, which are blocked, and what the last handoff for each lane said.

lune run parallax status          # project briefing, tasks, vault page, next step
lune run parallax board           # open the local web board on 127.0.0.1:8790

Starting a pipeline

The workflow is the same regardless of which pipeline you are in.

# 1. Start the lane with your request
lune run parallax start <lane> --prompt "<your request>"

# 2. Check the board
lune run parallax status

# 3. Claim a task
lune run parallax task claim <id> --as "what I will make"

# 4. Run the pipeline (commands depend on the lane — see that lane's page)

# 5. Record your verdict
lune run parallax verdict <kind> <name> <0-10> "..."

# 6. Hand off
lune run parallax handoff "what I did" --lane <lane> --next "..." --warn "..."
Note

Pipeline commands are blocked until you run lune run parallax start <lane>. The session token lasts four hours. If you get a gate error saying no session exists, run start again.
