Pipeline

QA

Tests a Roblox game like a tester: a security audit of every remote, a self-test that proves every content gate catches its bad fixture, scripted in-engine playtests with a performance probe driven through the Studio MCP, and a regression record where every bug you find becomes a spec case and a mutation case. Your verdict is the bar; the accept ratchet keeps it.

Tier 0 1 approval

At a glance

Makes
Audit results, selftest results, playtest result JSON files, and a regression record (tests/regressions.json) that keeps every confirmed bug alive as a runnable test.
Hardware
Tier 0 for audit, selftest, and mutation testing (run in Lune). Studio (installed locally) is required for in-engine playtests.
Your approvals
One: when you rate a feature 7 or above, run kit accept to register it as a regression floor. The kit refuses any future change that drops below it.
When to run
Before calling any feature done; after adding or changing remotes; when importing free models or third-party code; for a performance check.

The flow in one line

audit → selftest → playtest → record + accept (verdict ≥ 7)

The stages

  1. 1
    AuditStatic security check of every remote handler in the game.

    kit audit reads every OnServerEvent and OnServerInvoke handler in the game's server scripts. For each one it checks:

    • Every client argument is validated with Guard, typeof, type, or a check function.
    • The handler calls a RateLimit before doing any work.

    It also flags these patterns regardless of where they appear:

    • require(<asset id>): a numeric ID passed to require is a free-model backdoor.
    • loadstring: dynamic code execution.
    • Server-side InvokeClient: exploitable for denial of service.
    • getfenv / setfenv: environment manipulation.
    • FireAllClients inside a loop: a network flood.

    The audit runs automatically inside kit verify. If you have an intentional exception, record it:

    # In kit.config.json, add:
# "qa": { "auditIgnore": ["src/server/AdminService.luau:47"] }
# The entry must be exactly "file:line" (or "file", or "file:rule"); keep the reason in your notes, not in the string.
lune run parallax audit
  2. 2
    SelftestProve every content gate still catches its designated bad fixture.

    Every content gate (3D topology, VFX caps, remote schema, move validation, and so on) has a deliberately broken fixture in kit/selftest/<lane>/. kit selftest runs the gate against that fixture and fails if the gate does not catch it.

    This prevents "gate rot": a gate that has been loosened or broken without anyone noticing. Never edit a gate or its fixture to make something pass.

    kit vault check is a separate step that runs as part of kit verify. It checks the knowledge vault for missing frontmatter, broken wikilinks, and stale indexes.

    lune run parallax selftest
lune run parallax verify   # runs the audit and the vault check with every other gate (not selftest)
  3. 3
    PlaytestRun scripted checks inside a live Roblox Studio session through the Studio MCP.

    A playtest is a Luau script that runs inside a Studio play session and reports results as JSON. Its first line declares which side it runs on:

    -- runs on: Server

    Use the check API to write assertions:

    -- runs on: Server
return function(t)
    local player = t.player()
    if not t.check("player spawned", player ~= nil) then
        return
    end
    t.check("kit runtime present", t.find("ReplicatedStorage.kit") ~= nil)
end

    The script returns one function that receives t; the bundle calls it.

    Running through Studio MCP:

    1. kit playtest bundle <name>: compile the script.
    2. MCP: start_stop_play(true) to start a play session.
    3. MCP: execute_luau with the bundle code.
    4. Save the returned JSON.
    5. MCP: start_stop_play(false) to stop.
    6. kit playtest record <name> <file> to store the result.
    7. Skim get_console_output for errors from other scripts.

    Any console error (from any script, not just your playtest) fails the run. The performance probe (configured in qa.perf inside kit.config.json) measures memory, workspace instance count, and frame time against thresholds you set.

    lune run parallax new playtest smoke
lune run parallax playtest bundle smoke
# then run through Studio MCP (see above)
lune run parallax playtest record smoke build/playtest/smoke.json
  4. 4
    Record verdict ≥ 7 to acceptExploratory play, regression record, and the accept ratchet.

    After scripted playtests, play the game as a hostile player. Try things that should not work:

    • Spam a remote faster than its rate limit allows.
    • Send a request from far away (position outside the valid range).
    • Send a request while dead.
    • Have two players act simultaneously on the same object.
    • Leave in the middle of an action (disconnect during a combo, a shop transaction, a respawn).

    Every bug you find becomes a spec case and a mutation case:

    lune run parallax bug "shop charges twice on rapid click" \
  --spec tests/shop.spec.luau \
  --module src/shared/ShopRules.luau \
  --line "if cart.pending then" \
  --from "processPurchase(cart)" \
  --to "processPurchase(cart); processPurchase(cart)"

    Run kit mutate --regressions to replant all regression bugs and confirm your specs still catch every one of them.

    When you are satisfied with a feature, record your verdict and lock the floor:

    lune run parallax verdict system combat 8 "no exploits found, perf green"
lune run parallax accept system combat

Inputs and outputs

  • tests/playtest/<name>.luau: playtest scripts. First line declares side (-- runs on: Server or -- runs on: Client).
  • kit.config.json key qa.perf: performance thresholds (memoryMb, instances, heartbeatMs, clientMemoryMb, highlights, shadowLights, shadowRadius); a key you leave out uses the kit's default.
  • kit.config.json key qa.auditIgnore: accepted-risk entries, each exactly "file:line", "file" or "file:rule".
  • The game's server scripts (read by the audit).
  • The kit's selftest fixtures in kit/selftest/<lane>/ (read by selftest).
  • build/playtest/<name>.result.json: the playtest result, check by check, plus the console log.
  • tests/regressions.json: bug registry (every confirmed bug as a spec case and a mutation case). Never delete entries; add them.
  • Playtest verdicts in kit/knowledge/vault/qa/playtests/: one Markdown file per playtest type.

The QA pipeline does not add runtime modules to the game. It tests the modules added by the systems pipeline and verifies that the kit's own runtime is present and behaving correctly.

The built-in smoke playtest checks three things automatically: the player spawns alive, the kit runtime is present under ReplicatedStorage.kit, and the workspace stays stable while idle (fewer than 500 new instances over a 3-second wait).

The check API

Playtest scripts use a small API injected by kit playtest bundle. Each script returns function(t) ... end; the bundle calls it with t.

CallWhat it does
t.check(name, cond, detail?, fix?)Assert a boolean. detail is extra information logged on failure. fix is a suggested fix for the report.
t.wait(seconds)Pause the playtest for a fixed duration.
t.waitFor(fn, timeout?)Poll fn() until it returns true or the timeout (default 10 s) expires.
t.player(timeout?)Wait (default 15 s) for the first player with a spawned character, and return the Player.
t.find("A.B.C")Find an instance by dot-separated path from game. Returns the instance or nil.
 
-- runs on: Server
-- tests/playtest/health_smoke.luau
return function(t)
    local player = t.player(10)
    t.check("player joined", player ~= nil)

    local character = t.waitFor(function()
        return player and player.Character
    end, 8)
    t.check("character spawned", character ~= nil)

    local humanoid = character and character:FindFirstChildOfClass("Humanoid")
    t.check("humanoid exists", humanoid ~= nil)
    t.check("full health on spawn", humanoid and humanoid.Health == humanoid.MaxHealth, "Health: " .. tostring(humanoid and humanoid.Health))
end

Commands

# Start the lane (required before any pipeline command)
lune run parallax start qa --prompt "test the combat system"

# Static checks
lune run parallax audit                        # security audit alone
lune run parallax selftest                     # prove every gate catches its bad fixture
lune run parallax verify                       # the full gate (audit + vault check + every other gate; not selftest)

# Playtests
lune run parallax new playtest <name>         # scaffold tests/playtest/<name>.luau
lune run parallax playtest bundle <name>      # compile for Studio MCP
lune run parallax playtest record <name> <file>  # store result JSON

# Regression record
lune run parallax bug "<what>" \
  --spec <spec file> --module <module> \
  --line "<piece of the line>" \
  --from <as it is> --to <the bug>         # register a bug as spec + mutation case

lune run parallax mutate --regressions         # replant all regression bugs

# Verdict and accept ratchet
lune run parallax verdict <kind> <name> <0-10> "..."
lune run parallax accept <kind> <name>       # lock verdict ≥ 7 as regression floor

How it learns

QA has two compounding mechanisms: the regression record and the lesson vault.

Regression record

Every bug in tests/regressions.json is replanted by kit mutate --regressions on every future run. A spec that stops catching a regression is a failure. The record only grows; entries are never removed. Over time it builds a comprehensive hostile-input suite for the whole game.

Lesson vault

Record QA traps and techniques with kit lesson qa "...". Example: "a registered KeyframeSequence loads asynchronously in Edit mode; wait for track.Length > 0 before reading frame data."

Verdict ratchet

When you rate a feature 7 or above and run kit accept, no future change may regress it below that floor. The ratchet is the mechanism that makes QA permanent: once something is good, it stays good.

Playtest vault

Every completed playtest type (for example, a combat smoke test, a shop transaction test, a UI storybook test) is stored as a named Markdown file in kit/knowledge/vault/qa/playtests/. The next session starts by reading what has already been proven.

Known limits

Known limit

Studio is shared between sessions. Always call get_studio_state first to check whether another session is already running a play. Never close another session's play session.

Known limit

An unfocused Studio window renders at around 5 frames per second. Timing-sensitive checks (frame-exact hitbox windows, animation markers) may behave differently when Studio is not in focus.

Known limit

A server started inside a Lune job dies when the job ends. The kit starts its own servers outside the job (WMI breakaway, a per-launch token).

Known limit

Lune's stdio.prompt does not work in an agent shell. Any step that requires your direct input stays yours; it cannot be automated.

Known limit

A KeyframeSequence registered in Edit mode loads asynchronously. Wait for track.Length > 0 before reading its frame data, or checks will read an empty sequence.

A typical session

This is the shape of a complete QA session, from start to acceptance.

  1. Start the lane: lune run parallax start qa --prompt "test the combat system". Read the boot sheet and the last handoff.
  2. Run the static checks first (they are fast and GPU-free):
    • kit audit: fix any unvalidated arguments or missing rate limits.
    • kit selftest: confirm every gate is still catching its bad fixture.
    • kit verify: the full gate (audit + vault check + all other gates; selftest runs separately).
  3. Write a playtest for the core flow: kit new playtest combat_smoke. Add checks for spawn, kit runtime, and a basic attack landing.
  4. Bundle and run through Studio MCP. Record the result. Fix any console errors.
  5. Play the game as a hostile player. Try spamming, disconnecting mid-action, sending requests from outside the valid range. For every bug found, run kit bug to register it.
  6. Run kit mutate --regressions to prove all regression specs still pass.
  7. Record your verdict: kit verdict system combat 7 "no exploits, perf within budget". Run kit accept system combat.
  8. Hand off: kit handoff "QA green, 2 bugs found and registered" --lane qa --next "...".
